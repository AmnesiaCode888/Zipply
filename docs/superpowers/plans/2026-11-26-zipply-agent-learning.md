# Навыки, MCP и обучение на опыте в Zipply

Дата исследования — 26 ноября 2026. План развивает задачу 11 (P1.5) [текущего плана харнеса](2026-11-24-zipply-agent-harness.md). Исходный аудит зафиксировал состояние проекта до первого среза реализации; актуальный статус добавлен ниже.

## Целевой сценарий

Пользователь просит подготовить отчёт по результатам локальных тестов. Zipply находит подходящие навыки, загружает инструкции и при необходимости обнаруживает инструменты уже разрешённой интеграции. Если повторяемого процесса ещё нет, агент решает задачу обычными инструментами. После подтверждённого результата Zipply выделяет из опыта короткую процедуру с условиями применимости, проверяет её на другом примере и сохраняет версию. В следующем чате того же проекта навык находится сам. Пользователь может открыть источник, условия применения, результаты сравнения и откатить изменение.

В первом релизе агент самостоятельно создаёт и предлагает текстовые навыки проекта. Предложение можно активировать из чата или библиотеки. После проверки на серии задач пользователь сможет включить автоматическую активацию для этого проекта. Установка интеграций и разрешение передачи данных остаются отдельными действиями пользователя.

## Что уже сделано в первом срезе

- Убрано ограничение первичного списка 24 навыками. `search_skills` ищет по всей библиотеке и описаниям связанных инструментов; `load_skill` загружает только выбранные инструкции. При подготовке нового навыка `search_tools` находит точные ссылки среди инструментов этого запуска и возвращает только метаданные.
- Поддержаны связанные ссылки `core:`, `plugin:` и `mcp:` в `metadata.zipply_tools`. Zipply показывает описания для поиска и подключает ссылки при загрузке навыка. Плагин должен быть установлен; MCP-сервер — явно выбран в сообщении. Метаданные навыка не меняют разрешения и не запускают сервер.
- Добавлен `propose_skill`: модель сохраняет черновик переносимого `SKILL.md` с причиной и ID запуска. Черновики ограничены проектом, валидируются, хранятся вне активного дерева и остаются неактивными.
- В **Расширения → Навыки** доступны просмотр полного текста, подтверждённое принятие в `.agents/skills/` и удаление черновика. При принятии проверяются границы проекта; публикация не перезаписывает существующий навык.
- Формат и связи описаны в [руководстве по навыкам](../../agent-skills.md). `npm run typecheck` прошёл после этих изменений. Тесты не запускались.

Ограничения этого среза: единый поиск по всем типам расширений ещё не готов; MCP-связи не обнаруживают инструменты отключённого или не выбранного пользователем сервера; нет обновления существующего навыка, версий и отката, независимой оценки эффективности кандидата, фонового извлечения доказательств и автоматического режима. Предложения пока создаются агентом в рамках текущего запуска, а пользователь принимает их через библиотеку.

## Архитектура

Локальный каталог в main process объединяет представления над существующими `SkillRepository`, `PluginManager` и `McpRuntimeManager`. У источников остаются свои данные и жизненный цикл. Запуск получает ограниченный снимок разрешённых возможностей. Обновления MCP инвалидируют устаревшие записи и подтверждения, а публикация новой версии навыка влияет на следующие запуски. Содержимое уже выбранного навыка фиксируется на время текущего запуска.

```mermaid
flowchart LR
    C[Каталог возможностей] --> S[Поиск по задаче]
    S --> A[Загрузка навыка или схемы]
    A --> G[Проверка полномочий]
    G --> R[Выполнение и проверка результата]
    R --> E[Событие с подтверждённым результатом]
    E --> D[Черновик навыка]
    D --> V[Сравнение на новом примере]
    V --> P[Публикация версии]
    P --> C
```

- **Обнаружение.** По умолчанию передавать небольшой релевантный список метаданных в изменяемую часть контекста. `search_extensions` позволяет модели искать по всему разрешённому каталогу, уточнять запрос и получать следующую страницу. Начать с локального полнотекстового ранжирования по названию, описанию, ключевым словам и области действия. Русские и английские сценарии включить в eval. Векторный поиск добавить, если замеры показывают систематические пропуски по смыслу.
- **Активация.** Индекс возвращает `kind`, стабильный `id`, `revision`, источник и признаки доступности. `load_skill` получает серверную запись по `id` и `revision`. Загрузка MCP-инструмента добавляет полную схему в следующий запрос. Для ещё не подключённого сервера каталог может показать его назначение из настроек или кеша. Чтобы перечислить живые инструменты, харнес сначала проверяет право на соединение. Ручной выбор использует те же механизмы, включая `disable-model-invocation`, `user-invocable` и проверку ревизии.
- **Доверие.** До запуска stdio нужна явная регистрация и отдельное право на запуск в нужной области. До отправки аргументов MCP проверяются разрешение запуска, запись подключения, идентичность инструмента и снимок схемы. При изменении конфигурации, описания или схемы старое разрешение теряет силу. Аннотации MCP и `allowed-tools` из навыка описывают намерение автора. Полномочия выдаёт приложение. MCP-промпты, ресурсы, ответы сервера и импортированные инструкции остаются внешними данными с ограниченной ролью. Встроенные проверки политик применяются независимо от разметки в промпте. [MCP Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) · [Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) · [Security Best Practices](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices).
- **Хранилище навыков.** Стабильный логический ID для управляемых Zipply навыков, независимый от директории. Активная версия хранится отдельно от неизменяемых ревизий. Черновик ссылается на `baseRevision`. Публикация сверяет её с активной версией и обновляет указатель одной атомарной операцией. Перед публикацией проверять наличие исходного объекта и хеш пакета, включая ссылки и ресурсы, которые реально будут доступны. При конфликте сохранить черновик для пересмотра. Для существующих ссылок сохранить идентификаторы и проверку старого хеша.
- **Память.** `RunJournal` отвечает за восстановление исполнения. Короткие предпочтения и факты хранятся отдельными записями с источником, областью и временем проверки. Процедуры хранятся навыками. В первом релизе достаточно области проекта, идентифицированной в main process по каноническому workspace. Явно сохранённые пользовательские предпочтения можно добавить отдельным этапом. Для фактов с изменчивым состоянием нужен срок актуальности или перепроверка.
- **Обучение.** После успешного завершения main process записывает минимальное событие `RunLearningEvidence`. Поля — ID задачи и проекта, исход, проверенные критерии, ID и ревизии применённых навыков, ссылки на разрешённые свидетельства и явная обратная связь. Повторяющийся проверенный процесс или явная команда обучения ставят работу в ограниченную очередь. Ошибка становится учебным сигналом после подтверждённого исправления. Отменённые и непроверенные запуски не дают признака успеха. Полные переписки, секреты, вывод терминала и вложения не передаются автоматически. Для облачного провайдера фоновое использование данных требует настройки пользователя. Очередь выдерживает повторный запуск и не блокирует финальный ответ.
- **Проверка черновика.** Автор получает ограниченный вход и возвращает типизированное предложение. У него доступны чтение одобренных фактов и запись черновика через сервис. Проверяющий запускает кандидат и базовую версию на одинаковых независимых локальных примерах с одним и тем же провайдером, набором инструментов и бюджетом. Задание отличается от исходного, а ожидаемый результат изолирован от модели. При недостатке проверяемых примеров показывать «требуется проверка» и оставлять решение пользователю. Включённая пользователем автоактивация распространяется на новые текстовые версии навыков текущего проекта после прохождения проверок.

Предлагаемые режимы — `off`, `propose`, `auto`. Для нового проекта после включения обучения использовать `propose`. `off` останавливает очередь, но активные навыки доступны. `auto` ограничен уже включённым проектом и текстовыми навыками, созданными Zipply. Проектные файлы, навыки из чужих каталогов, конфигурации интеграций, hooks, скрипты и разрешения исключены из фоновой записи. Пакеты с исполняемыми компонентами требуют отдельного механизма установки и изоляции.

### Почему этот вариант

1. **Один инструмент записи навыков.** Самый быстрый прототип. Показывает, что модель может написать `SKILL.md`, но оставляет существующий лимит обнаружения, отсутствие истории версий и невозможность измерять пользу.
2. **Каталог плюс проверяемый цикл обучения.** Использует существующие хранилища, исполнители и `npm run agent:eval`. Позволяет измерять поиск отдельно от качества навыка и выпускать этапы по одному. Это предлагаемый вариант.
3. **Встроить внешний харнес.** Даёт готовые функции, но переносит часть контроля в отдельный рантайм и усложняет согласование с Zipply IPC, проектными правилами, permissions и восстановлением диалога. Подходит для отдельного совместимого бэкенда при появлении соответствующей задачи.

Сначала обычный запрос в новом чате должен находить уже настроенный MCP в своей области и пользоваться им через одну операцию поиска со схемой. Затем понадобится общий маршрут установки и входа. Каталог DeepWiki уже проверяет возможность соединения из чата, а расширять список серверов имеет смысл после общей модели доступности. Для обучения ближайший сценарий — `/learn`, правка существующего навыка, diff и отмена прямо из чата.

## Критерии готовности первого релиза

1. Установленный навык после 24-й позиции находится по запросу и самостоятельно применяется к подходящей задаче. Запрещённый к автоматическому вызову навык доступен только через разрешённый ручной маршрут.
2. Модель сама обнаруживает отдельный инструмент заранее разрешённой MCP-интеграции. До первого запроса к серверу применяются правила подключения, а новый вызов получает разрешение для своего дескриптора и передаваемых данных. Отключённый сервер не запускается из-за запроса к каталогу.
3. Из проверенной задачи получается черновик с источником и результатом сравнения. В новом чате появляется только активная версия. Откат переживает перезапуск. Сбой обучения не меняет статус исходной задачи.
4. Кандидат лучше базовой версии минимум по одному заранее заданному критерию и не ухудшает обязательные проверки или выбор навыка на отрицательных запросах. Источник кандидата отделён от контрольных задач. Для пилота публикуются размер набора, успешность, ложные срабатывания, медиана токенов, вызовы и задержка. Порог для широкой автоактивации выбирается по результатам пилота.
5. Покрыты отмена, перезапуск, конкурентные версии, смена разрешения, изоляция между проектами, скрытие секретов и отсутствие команд у фонового автора. «Выведенная моделью уверенность» имеет нулевой вес в назначении прав или зачёте проверки.
