# План реализации инструментов агента Zipply

> План состоит из трёх самостоятельно проверяемых частей. Реализация — отдельная задача; решения ниже являются предлагаемыми настройками первой версии.

**Цель:** улучшить понимание кода, управление длительными командами и согласованное изменение нескольких файлов.

**Архитектура:** инструменты реализуются в основном процессе Electron через существующие `ToolBase`, `ToolRegistry` и `ToolExecutor`. Состояние долгих процессов живёт в отдельном сервисе приложения; остальные инструменты получают актуальное состояние проекта на каждый вызов.

**Стек:** Electron, Node.js, TypeScript, React; тесты — `node:test` и существующий загрузчик через esbuild.

**Основание:** запрос на инструменты 1, 3 и 5 и фактическое состояние проекта на 3 ноября 2026 года. Отдельной утверждённой спецификации нет; этот документ фиксирует предлагаемый объём и критерии приёмки.

## Исходное состояние

- `src/main/agent/index.ts` подключает оба набора инструментов; `ToolExecutor` отвечает за политики, подтверждения, кэш и события.
- `AgentRunner` создаёт новый `Blackboard` на каждый запуск. Следовательно, он не подходит для хранения процессов между сообщениями.
- `terminal` ожидает завершения команды, по умолчанию 60 секунд, передаёт вывод и завершает дерево процессов при отмене или тайм-ауте.
- `edit_file` уже принимает несколько точных непересекающихся замен **одного** файла; новый инструмент нужен для набора файлов. В текущем `ToolExecutor` пути файлов и команды перечислены явно, как и инструменты предварительного просмотра в `AgentRunner`.
- `requestId` создаётся для каждого сообщения, а идентификатор чата `session.id` сейчас остаётся в renderer. Чтобы изолировать процессы чатов между запросами, его нужно явно передать в main и проверить границы владения.
- В рабочем дереве уже есть несохранённые изменения. При реализации учитывать актуальное состояние файлов и не перезаписывать чужие изменения.

## Общие ограничения и контрольные случаи

- Сохранить существующие инструменты и форматы сохранённых чатов; в режиме плана и только для чтения исключать изменяющие операции.
- Никакой незаявленной установки пакетов в проект пользователя или запуска его скриптов для диагностики.
- Проверять реальные пути, включая ссылки и junction; не допускать обхода разрешений при переходе к новым инструментам.
- Ограничивать объём вывода, памяти и время ожидания; явно сообщать об усечении и недоступных результатах.
- Интерфейс: следовать `AGENTS.md`: нейтральные поверхности, отсутствие теней и обводок у контролов, скругления, размеры текста; состояния видны по тексту и доступны с клавиатуры.
- Проверить отдельно: символьные ссылки за пределы проекта; параллельное изменение файла после подготовки; отказ в записи посреди пакета; отмену в момент старта процесса; переход между двумя чатами с одним workspace.

## Порядок реализации

1. `code_intelligence`: самостоятельный инструмент без зависимости от остальных.
2. `process`: отдельный сервис для управления командами между сообщениями.
3. `apply_patch`: многофайловые правки и просмотр результата.
4. Совместная проверка сценария: исследовать код → изменить несколько файлов → запустить проверку → получить результат.

Каждый этап заканчивается регистрацией инструмента, проверкой доступа, отображением событий и собственным набором тестов. Коммиты или интеграция выполняются только по отдельному решению пользователя.

## Часть 1. Диагностика и навигация по коду

### Объём первой версии

Инструмент `code_intelligence` поддерживает `definition`, `references` и `diagnostics` для файлов TypeScript и JavaScript (`.ts`, `.tsx`, `.js`, `.jsx`). Для навигации нужны путь, строка и столбец; пользовательские координаты — с единицы. Для диагностики достаточно пути к файлу. Результат содержит относительный путь, строку и столбец; ошибки — также код, уровень и сообщение. Ограничение — 100 результатов и 25 000 символов с явной пометкой об усечении.

**Подход:** встроенный TypeScript Language Service как первый адаптер. Он использует уже знакомую проекту экосистему и даёт значения без запуска отдельного LSP-сервера. На следующих этапах адаптер можно заменить или дополнить LSP для других языков. Проверить упаковку TypeScript в production Electron: текущая зависимость находится в `devDependencies`; перенести её в runtime-зависимости или иным образом гарантировать наличие в итоговой сборке. Не загружать плагины TypeScript, скрипты и локальные исполняемые модули анализируемого проекта.

### Файлы

- Создать `src/main/agent/services/TypeScriptAnalysis.ts` — изолированный адаптер TypeScript Language Service и чтение конфигурации.
- Изменить `src/main/agent/tools/ToolRegistry.ts`, `src/main/agent/index.ts`, `src/main/agent/core/ToolExecutor.ts`, `src/main/agent/core/PromptProviders.ts` — регистрация, доступ к путям, стратегия использования.

   - [ ] Ограничить анализ файлов и выдачу результатами внутри workspace; для внутренних файлов TypeScript может читать библиотеки и зависимости, но внешние исходники и диагностику не возвращать без отдельного разрешения.    - [ ] Тесты на импорты между двумя файлами, одноимённые символы, Unicode/CRLF, реальную ошибку типа, отсутствие конфигурации, отмену/тайм-аут и отсутствие запуска тестового плагина.

**Критерий готовности:** агент находит определение и использования символа в другом файле, возвращает настоящую ошибку типа и после внешнего изменения файла показывает актуальный результат. Неподдерживаемый язык сообщает об ограничении.

## Часть 2. Долгоживущие процессы

### Объём первой версии

Набор состоит из четырёх инструментов: `process_start`, `process_poll`, `process_stop`, `process_list`. `process_start` принимает `command` и необязательный `cwd`; возвращает непрозрачный `processId` и начальный статус, не ожидая завершения. `process_poll` принимает `processId`, необязательные `cursor` и `wait_ms` до 10 000 мс; возвращает новые строки и следующий курсор. `process_stop` завершает только процесс, созданный Zipply для текущего чата. `process_list` показывает процессы текущего чата. Интерактивный stdin и PTY в первую версию не входят.

Процесс живёт между сообщениями одного чата и прекращается при удалении чата, явной остановке или выходе из приложения. Отмена активного ответа останавливает процессы, запущенные **этим** запросом; обычное успешное завершение ответа их не останавливает. После перезапуска приложения процессы не восстанавливаются.

### Файлы

- Создать `src/main/agent/services/ProcessManager.ts` — реестр, запуск, буфер, состояние, уборка.
- Создать `src/main/agent/tools/ProcessTool.ts` — валидация действий и вызов сервиса.
- Изменить `src/main/agent/tools/TerminalTool.ts` и при необходимости выделить общий `src/main/agent/services/ShellProcess.ts` — использовать одинаковое поведение shell и завершения дерева.
- Изменить `src/preload/index.ts`, `src/preload/index.d.ts`, `src/main/ipc/AgentIpcHandler.ts`, `src/renderer/src/hooks/useChat.ts` — передать стабильный `session.id`, обработать удаление и отмену, изолировать владельцев.
- Изменить `src/main/index.ts`, `ToolRegistry.ts`, `src/main/agent/index.ts`, `ToolExecutor.ts`, `PromptProviders.ts` — жизненный цикл приложения, доступ и регистрация.
- Создать `tests/process-manager.test.cjs`, `tests/process-tool.test.cjs`, дополнить IPC и UI тесты.

### Задачи

1. **Идентификация владельца и жизненный цикл.**
   - [ ] Передать `sessionId` отдельно от `requestId` в обычной отправке и повторном запуске; в main связать процесс с `(senderId, sessionId)` и каноническим workspace. Проверять владение на каждом вызове; смена workspace не даёт управлять старыми процессами другого workspace.
   - [ ] Добавить внутренние операции `stopRequest(owner, requestId)`, `stopSession(owner)`, `shutdown()`. Подключить их к отмене, удалению чата и выходу; при закрытии/уничтожении renderer очищать его процессы. Переключение между чатами само по себе процессы не останавливает.
   - [ ] Тесты: два чата с одной папкой изолированы, другой renderer не видит процесс, повторная отправка в том же чате видит его, удаление и завершение приложения освобождают процессы.
2. **Менеджер процессов.**
   - [ ] Реализовать запуск через тот же PowerShell/Bash и скрытое окно, что и `terminal`; использовать UUID и не принимать произвольный системный PID для остановки.
   - [ ] Состояния: `starting`, `running`, `exited`, `failed`, `stopped`; возвращать код выхода и сигнал, если известны. Однократно обрабатывать ошибки spawn/close и очистку слушателей.
   - [ ] Хранить до 256 КБ вывода на процесс с порядковым курсором; если запрошенный курсор устарел, вернуть доступный фрагмент и флаг `truncated`. Ограничить до 5 активных процессов на чат и 20 на приложение; завершённые записи хранить не более 30 минут.
   - [ ] `poll` ожидает не более `wait_ms`, прерывается по AbortSignal; тайм-аут ожидания не завершает процесс. Обработать выход до первого `poll`, пустой вывод, ошибку команды и переполнение буфера.
   - [ ] При остановке завершать дерево: существующий `taskkill /T /F` на Windows, процессную группу на Unix; дожидаться подтверждения завершения и сообщать ошибку, если это не удалось. Учесть гонку отмены со `spawn` и повторный `stop`.
3. **Политика и отображение.**
   - [ ] `process_start` и `process_stop` классифицировать как изменяющие; `process_poll` и `process_list` — как чтение без кэширования. Это отдельные определения инструментов, чтобы существующий `buildToolDefs`, фильтрующий политики без аргументов, скрывал изменяющие действия в plan/read-only.
   - [ ] На `start` применять ту же политику подтверждения команд, что у `terminal`, включая `requiresConfirmation`, рабочую папку и текущий режим доступа. При проверке пути cwd и владельца не полагаться на данные из модели.
   - [ ] Показывать команду, состояние, код выхода и последние строки в карточке; на стороне агента объяснить, что `poll` после завершения ответа возможен только для процесса того же чата.
   - [ ] Тесты на подтверждение/отказ, read-only, опасную команду, разные workspace, лимиты, отмену старта, остановку дочернего процесса и стабильный курсор.

**Критерий готовности:** агент запускает тестовый сервер, получает вывод в следующем сообщении того же чата и останавливает его без воздействия на другие чаты. Обычный `terminal` продолжает работать как раньше.

## Часть 3. Пакет правок `apply_patch`

### Объём первой версии

Использовать структурированный JSON вместо разбора произвольного unified diff: `operations` — массив до 20 операций `{ path, action: 'create' | 'update' | 'delete', ... }`. Для `update` передаются `edits: [{ target, replacement }]` — точные уникальные непересекающиеся фрагменты **исходного** файла, как в пакетном режиме `edit_file`; для `create` — полный `content`; для `delete` — ожидаемый SHA-256 исходных байтов, чтобы не удалить изменившийся файл. Один путь встречается не более одного раза. Переименование и бинарные файлы в первую версию не входят.

Сначала подготовить и проверить весь пакет, затем показать совокупный diff и получить подтверждение согласно режиму доступа. Отказ или ошибка подготовки не изменяют ни один файл. Файловые системы не дают общей атомарной транзакции на несколько файлов: при ошибке посреди записи выполнять best-effort откат и честно сообщать, какие пути удалось восстановить, а какие нужно проверить вручную.

### Файлы

- Создать `src/main/agent/tools/ApplyPatchTool.ts` — контракт, подготовка и выдача результата.
- Создать `src/main/agent/services/PatchTransaction.ts` — проверки, снимки исходных байтов, временные файлы, применение и откат.
- По возможности вынести общий чистый алгоритм точных замен из `EditFileTool.ts` в `src/main/agent/tools/textEdits.ts` без изменения существующего поведения одиночной замены.
- Изменить `ToolExecutor.ts`, `AgentRunner.ts`, `ToolRegistry.ts`, `src/main/agent/index.ts`, `PromptProviders.ts` — доступ, единое подтверждение подготовленного diff, регистрация и отображение.
- Изменить `src/shared/agentEvents.ts`, `src/renderer/src/hooks/useChat.ts`, `src/renderer/src/types/chat.ts`, `src/renderer/src/components/tools/ToolCallCard.tsx` и `CommandApproval.tsx` по необходимости для списка файлов и читаемого diff.
- Создать `tests/apply-patch.test.cjs`, `tests/patch-approval.test.cjs`, дополнить тесты доступов и карточек.

### Задачи

1. **Валидация и подготовка без записи.**
   - [ ] Валидация: 1–20 файлов, 1–50 замен на файл, максимум 1 МБ входных данных и 2 МБ исходного файла, только UTF-8 текст; запрет повторяющихся канонических путей, директорий, бинарных файлов и неоднозначных/пересекающихся замен.
   - [ ] Для каждого пути вызвать `inspectWorkspacePath`; подготовить исходные байты, хэш, метаданные, новый контент и diff. Существующий файл для `create` и отсутствующий для `update`/`delete` — ошибка. Сохранять формат конца строк и права существующих файлов.
   - [ ] Внешние пути и ссылки проверять для **каждой** операции; для первой версии отклонять любые пути вне workspace с понятным сообщением. Проверять канонический путь повторно перед применением. Внутренние пути не классифицировать по одному только тексту `../`.
   - [ ] Тесты: успешные изменения двух файлов; отсутствующий/неоднозначный target во втором файле оставляет первый неизменным; дубли, binary, CRLF, внешняя symlink и превышение лимита.
2. **Предпросмотр и разрешение.**
   - [ ] Построить один предварительный просмотр со списком операций и diff каждого файла из подготовленных данных. Не изменять диск до подтверждения; в режиме `confirm` показывать одно подтверждение пакета, в `automatic` соблюдать текущие настройки, в read-only и плане запрещать вызов.
   - [ ] После подтверждения повторно проверить путь, тип файла и SHA-256 исходных байтов. При несовпадении отменить весь пакет до начала записи и сообщить конфликт. Не пересоздавать diff из другого набора входных данных после подтверждения.
   - [ ] Обновить `AgentRunner`: существующий `tool_baseline` поддерживает один файл, поэтому для пакета использовать явную структурированную информацию о файлах; сохранить обратную совместимость старых событий и чатов.
   - [ ] Тесты: отказ не пишет; план/read-only блокируют пакет; редактирование пользователем во время подтверждения вызывает конфликт; UI показывает все пути и правильный статус.
3. **Применение и восстановление.**
   - [ ] Подготовить временные файлы рядом с целями, сохранять права; перед заменой проверять хэши/пути. Создание выполнять с защитой от перезаписи. Сохранять исходные байты для восстановления, не записывая их в историю чата.
   - [ ] Последовательно применить изменения и собрать список реально затронутых файлов. При ошибке выполнять обратные действия в обратном порядке, предварительно проверив, что текущие файлы не изменились посторонним процессом; не перезаписывать чужие новые данные при восстановлении.
   - [ ] Отдельно сообщать `applied`, `restored`, `unrecovered` и причину; не утверждать полную атомарность при падении приложения или потере питания. Очищать временные файлы при обычном завершении и ошибке.
   - [ ] Тесты с искусственной ошибкой второй записи, ошибкой отката и посторонней правкой при откате; успешные `create`, `update`, `delete`; сохранение разрешений и CRLF.
4. **Интеграция.**
   - [ ] Зарегистрировать `apply_patch` у обоих агентов; в подсказке обозначить, когда использовать его вместо `edit_file`.
   - [ ] Показывать общий результат и раскрываемый список файлов с существующим `DiffViewer`, сохраняя дизайн проекта и доступность длинных путей/ошибок.
   - [ ] Проверить, что кэш чтения в `ToolExecutor` очищается после успешного применения и после любой частичной записи, включая неудачный откат.

**Критерий готовности:** агент показывает пакет правок для нескольких файлов, применяет корректный пакет и не изменяет файлы при ошибке подготовки или отказе. При ошибке во время записи результат честно описывает состояние каждого затронутого файла.
