# Доступность и установка MCP в Zipply

## Намерение

Пользователь один раз устанавливает или настраивает MCP-сервер, после чего агент находит его подходящие инструменты в новом чате без ручного прикрепления и без отдельного шага загрузки схемы. Агент может найти сервер в публичном каталоге и запросить первое подключение из чата.

## Цели

- Использовать официальный MCP Registry вместо встроенного списка из одного сервера.
- Искать записи каталога по имени и показывать поддерживаемые удалённые Streamable HTTP endpoint.
- Подключать только после явного согласия с показом адреса; хранить подключение в профиле пользователя.
- В следующих чатах находить инструменты уже настроенных серверов через обычный поиск тулов.
- Подгружать ограниченное число совпавших схем перед следующим запросом модели, не предлагая отдельный обязательный load.
- При каждом внешнем вызове применять текущую политику и разрешение по конкретному дескриптору; разрешение «запомнить инструмент» привязать к схеме.
- Оставить произвольный локальный stdio-сервер на существующем экране MCP, где пользователь задаёт исполняемый файл, аргументы и секреты.

## Не входит

- Выполнение npm/pip/OCI пакетов из публичного каталога без отдельного механизма проверки и платформенной установки.
- OAuth-поток. Серверы, требующие входа или секрета, остаются на ручной настройке в расширениях.
- Публикация в MCP Registry или обещание, что его саморепортируемые записи безопасны.
- Автоматическое доверие ко всем инструментам сервера только из-за режима полного доступа.

## Подтверждённое состояние

Конфигурации MCP уже лежат в профиле пользователя, а runtime подключает серверы по запросу. Однако доступ к инструментам дополнительно хранится во временной карте конкретного чата. Поэтому новый чат не видит ранее подключённые серверы. Для выбора MCP модель делает search_tools, затем manage_mcp(load). Установка из инструмента ограничена статическим DeepWiki. Каждый MCP-вызов отдельно проходит существующую проверку доверия/подтверждения.

## Подходы

1. Оставить каталог статическим и расширять список вручную. Это не масштабируется и снова привязывает продукт к известным заранее endpoint.
2. Использовать официальный read-only Registry для поиска удалённых серверов, хранить установленные endpoint в профиле пользователя, обнаруживать их при вызове search_tools и автоматически активировать только несколько совпадений. Это использует открытый формат каталога и оставляет согласие на границе подключения. Этот подход выбран.
3. Автоматически импортировать локальные пакеты из Registry. Это добавляет установку исполняемого кода, окружения и секретов на нескольких ОС; для этой реализации граница слишком широка.

## Поведение

Каталог MCP является внешним и недоверенным. Его поиск идёт по endpoint GET /v0.1/servers с version=latest; локальный кэш ограничен по сроку и размеру. Запись без поддерживаемого удалённого Streamable HTTP endpoint можно найти, но нельзя установить из чата этим маршрутом.

Установка из каталога и добавление произвольного удалённого URL проходят через существующий MCP confirmation card, показывающий источник, сервер и полный адрес. Сначала соединение проверяется во временном runtime; конфигурация сохраняется только после успешного MCP handshake. Первая попытка вызова найденного инструмента показывает параметры и позволяет либо разрешить один вызов, либо запомнить ровно эту схему.

После успешной настройки MCP-сервер принадлежит профилю приложения, а не чату. search_tools подключает ранее настроенные серверы только если агенту понадобился поиск внешних тулов, включает их описания в ранжирование и активирует не более трёх верхних совпадений для следующего запроса модели. Отключённый сервер не запускается простым перечислением расширений. Ошибка сервера не мешает пользоваться остальными инструментами.

Режим полного доступа убирает лишние подтверждения для обычной работы с файлами проекта и shell в рамках действующих настроек. Он не отменяет подтверждение первого подключения внешнего сервера и отдельного внешнего MCP-вызова. Уже запомненное разрешение действует только для совпадающего server ID, tool ID и fingerprint схемы; после смены схемы требуется новое решение.

## Ограничения формата

- Принимать только корректные записи официального Registry и поддерживаемый Streamable HTTP transport.
- Для публичных записей принимать только HTTPS endpoint. Для явно заданных пользователем локальных/частных адресов применяется существующий валидатор конфигурации.
- Не переносить значения секретных переменных из каталога в конфигурацию или модель.
- Локальный stdio конфигурировать через текущую форму MCP; процесс запускается только после подключения пользователем.
- Описания и схемы MCP остаются недоверенными данными и не меняют полномочия инструмента.

## Основание

Официальная документация определяет Registry как read-only каталог с версионированным API и поиском по имени. Она предупреждает, что записи предоставлены авторами серверов, Registry находится в preview и не даёт гарантий доступности или устойчивости данных. См. официальные [рекомендации клиентам Registry](https://github.com/modelcontextprotocol/registry/blob/main/docs/modelcontextprotocol-io/registry-aggregators.mdx), [спецификацию API](https://github.com/modelcontextprotocol/registry/blob/main/docs/reference/api/openapi.yaml) и [объявление Registry](https://blog.modelcontextprotocol.io/posts/2025-09-08-mcp-registry-preview/).
